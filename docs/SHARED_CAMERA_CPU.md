# 차선·주차 정지선의 영상 수신 공유

`use_stopline:=true`일 때 `lane_main`과 `stopline`을 같은 프로세스에서 실행하고 원본 영상 구독과 BGR 변환을 한 번만 수행한다. 두 ROS 노드의 이름·파라미터 범위·출력 토픽·검출 알고리즘은 유지한다. 프레임 순서대로 정지선과 차선을 처리하며 프레임을 생략하지 않는다. YOLO·주차·미션 제어는 별도 프로세스를 유지한다.

작은 영상 연산에 과도한 OpenCV 작업 스레드가 생기지 않도록 공유 프로세스는 기본 1스레드를 사용한다. `shared_opencv_threads`는 `lane_main`의 시작 파라미터다. 0이면 OpenCV 기본값을 유지한다. 실행 중 파라미터 변경은 적용하지 않는다.

기존 두 프로세스 방식은 다음처럼 선택할 수 있다.

```bash
ros2 launch clothoid_bringup full.launch.py use_stopline:=true share_lane_camera:=false
```

정지선 노드를 끈 구성(`use_stopline:=false`)은 기존 독립 차선 노드와 OpenCV 설정을 유지한다. 기존 단독 `stopline` 실행도 지원한다. 공유할 두 노드의 image_topic이 다르면 시작하지 않는다.

리모2에서 같은 bag 구간 600장의 RGB 영상을 30fps로 보내 old/new/new/old 순서로 비교했다. JPEG 디코딩·영상 발행 프로세스는 측정 대상 노드 CPU에서 제외하고 모든 실행에 동일하게 사용했다. 하드웨어 드라이버·YOLO를 함께 실행한 전체 주행 측정은 아니다.

| 항목 | 기존 두 프로세스 | 영상 공유·OpenCV 1스레드 |
|---|---:|---:|
| 합산 CPU, 한 코어=100% | 129.4~130.4% | 71.5~71.6% |
| 처리 프레임 수/입력 | 600/600 | 600/600 |
| 정지선 true 프레임 | 26 | 26 |
| 차선 응답 p95 | 23.6~24.0ms | 25.4~26.6ms |
| 정지선 응답 p95 | 16.6~17.9ms | 9.7~10.0ms |

해당 입력에서 차선 검출 결과·목표점·지그재그·좌우 점 목록·정지선 판정·최종 Twist 명령의 불일치는 0건이었다. 차선 응답에는 약 2ms의 추가 지연이 있어 모든 지연이 줄었다고 해석하면 안 된다. 약 45% 절감은 위 두 노드의 합산 CPU에 대한 수치이며 전체 차량 CPU 절감률은 아니다. 실제 주행에서는 카메라·YOLO·미션을 함께 실행한 부하와 지연을 추가 관찰해야 한다.

검증은 기존 판정을 보존하는 것이므로 횡단보도 마지막 가로선의 주차 조기 진입 문제와 주차 목표 고정 문제를 해결하는 변경이 아니다.
