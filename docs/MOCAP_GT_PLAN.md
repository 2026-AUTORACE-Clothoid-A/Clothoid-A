# 모션캡처 GT로 주행 중 위치 추정 검증하기: 오프라인 비교 계획

작성: 주영(통합/MUX) · 2026-11-12 · 상태: 제안. 코드 변경은 아직 없음.

## 1. 목적
연습장 모션캡처로 LIMO의 한 바퀴 궤적(GT)을 기록한다. 이 GT를 기준으로 차 안의 `/imu` yaw + `/odom` 속도 dead reckoning이 얼마나 정확한지 오프라인으로 잰다.
결과로 다음 두 가지를 정한다.

- **미션 예측:** 주행 중 "코스에서 지금 어디쯤인지"를 알아 다음 미션을 미리 준비(검출 게이팅, 노드 켜기)하는 데 쓸 수 있는가.
- **재시작 대비:** 미션 실패로 시작점에서 다시 출발할 때 위치를 체크포인트로 리셋해서 쓸 수 있는가. 3차선 구간에서 몇 번째 차로인지 판단할 수 있을 만큼 횡방향 정확도가 나오는가.

위치 정보는 판단을 **보조**하는 용도다. mux 우선순위와 각 미션의 센서 판단은 그대로 둔다. 회피와 라바콘 구간은 로컬 경로가 우선이다.

전제:
- 규정상 문제없음.
- 대회장은 대회 측 도면과 같은 배치·치수.

## 2. 데이터 수집
| 항목 | 내용 |
|---|---|
| 마커 | LIMO 상판에 flexible ball 3개 이상(비대칭 배치, rigid body로 등록) |
| 주행 | **RC로 이상적인 선을 따라 한 바퀴**(차로 중앙, 미션 경로는 사람이 의도한 대로). 2~3바퀴 반복 |
| 동시 기록 | `ros2 bag record /imu /odom /scan /camera/color/image_raw /cmd_vel /detections` + 모션캡처 원본(시각, x, y, z, 자세) |
| 시작 자세 | 매번 출발선의 같은 위치와 같은 방향에 놓고 2초 정지한 뒤 출발 |
| 측정 | 마커 rigid body 원점과 차 기준점(후륜축 중심) 사이 오프셋을 줄자로 잼 |

**RC 주행으로 GT를 따도 괜찮은 이유:**
- 모든 자율주행 미션이 아직 완성되지 않았다.
- GT는 우리가 다니려는 기준 경로이므로, 사람이 몬 이상적인 선이 오히려 맞다.
- 1105 bag에서 RC 주행 중에도 `/odom` 속도가 80~92% 구간에서 나왔으므로 dead reckoning 검증이 가능하다.

**나중에 할 것:** 자율주행이 안정되면 같은 방식으로 1바퀴를 더 기록한다.
- 이 기록은 "자율주행 궤적과 GT의 차이"(차선 추종 횡방향 오차, 회피 궤적)를 재는 데 쓴다.
- GT를 다시 딸 필요는 없다.

## 3. 전처리
1. **시간 맞추기:** 모션캡처 yaw rate와 `/imu` z 각속도의 상호상관으로 시간 오프셋을 구한다. 목표 오차는 10 ms 이하다.
2. **좌표 맞추기:**
   - 출발 정지 구간의 GT 자세를 원점(0, 0, yaw 0)으로 옮긴다.
   - 마커와 차 기준점 사이 오프셋을 보정한다.
3. **도면 정합:**
   - GT 궤적을 도면 좌표에 겹친다(출발선과 직선 구간 2곳으로 회전·평행이동).
   - 도면에서 체크포인트 위치를 뽑는다(정지선, 구간 경계, 미션 시작점).
4. **기준 경로:**
   - GT를 5 cm 간격으로 다시 샘플링해 `(s, x, y, yaw)` 표를 만든다. 약 800점이다.
   - 체크포인트 표 `(이름, s, x, y, yaw)`도 만든다.

## 4. 측정 항목
dead reckoning은 1105 분석과 같은 방식이다: `/imu` 자이로 yaw + `/odom` 속도.
- `/odom` yaw는 실제의 약 1.85배라 쓰지 않는다.
- `/odom` 속도가 빈 구간은 직전 값을 유지하고, 빈 비율을 같이 기록한다.

| # | 항목 | 정의 | 판단 기준(초안) |
|---|---|---|---|
| M1 | 진행 오차 | 추정 위치를 기준 경로에 투영한 `s`에서 GT `s`를 뺀 값. 구간별 최대·RMS | 미션 구간 간격(수 m)보다 충분히 작을 것. 목표 < 0.3 m |
| M2 | 횡방향 오차 | 추정 위치와 GT 사이 경로 법선 방향 거리. 구간별 | 3차선 구간 차로 판단에 쓰려면 < 0.1 m |
| M3 | heading 오차 | 추정 yaw − GT yaw, 바퀴 끝에서의 누적 | 1105 지도에서 본 약 2°/바퀴 수준인지 확인 |
| M4 | `/odom` 속도 배율 | `/odom` 적분 거리 ÷ GT 거리 | 배율을 보정값으로 저장 |
| M5 | 이벤트 보정 효과 | 아래 5절의 보정 A/B/C별로 M1, M2를 다시 계산 | 보정 후 M1 < 0.15 m 목표 |
| M6 | 재시작 시뮬레이션 | 체크포인트에서 리셋하고 다음 체크포인트까지 M1, M2 | 첫 바퀴와 같은 수준인지 |

**구간 나누기** (1105 bag 01 기준, 도면으로 확정): 출발·서행 → 우측 코너·지그재그 → 횡단보도(보행자) → 3차선 정적 장애물 → 갈림길 → 라바콘 → 좌측 직선 → 안쪽 차선 횡단보도(신호등) → 주차 구역

## 5. 이벤트 보정 방식 (비교 대상)
| 방식 | 내용 |
|---|---|
| A. 보정 없음 | 출발부터 dead reckoning만 |
| B. 진행 방향 보정 | 정지선, 횡단보도, 미션 완료(`/done`) 같은 확실한 이벤트에서 `s`를 그 지점의 체크포인트 값으로 맞춤 |
| C. B + 횡방향 보정 | 직선 구간에서 차선이 양쪽 다 잡히면 위치를 기준 경로 쪽으로 당김(가중치 0.1~0.3) |

- 이벤트 시각은 bag 안의 실제 검출기 출력을 쓴다(오프라인 도구로 재생).
- 오검출로 생긴 잘못된 보정도 결과에 포함한다. 예: 1105 분석에서 정지선 검출이 "천천히" 글자에 반응한 경우.

## 6. 부하 확인
위치 추정을 차에 넣었을 때 예상되는 연산은 다음과 같다.
- dead reckoning: `/odom` 콜백마다 삼각함수 몇 번
- 경로 조회: 직전 위치 주변 ±50점만 탐색
- 출력: 10 Hz

YOLO나 이미지 수신에 비해 무시할 수준으로 예상한다. 확인할 것은 하나다.
- Python으로 `/imu`를 전부 구독하면 메시지 오버헤드로 수 % CPU가 나올 수 있다.
- 오프라인 단계에서 `/imu`를 `/odom` 주기로 줄였을 때 M3가 나빠지는지 같이 본다.
- 나중에 차에서 `top`으로 실측한다.

하지 않을 것: 라이다 scan matching(ICP, AMCL 등). 무겁고, 이 용도에는 필요 없다.

## 7. 산출물
- `gt_path.csv` (`s, x, y, yaw`), `checkpoints.yaml`
- 구간별 M1~M6 표, 바퀴별 그래프(추정 궤적과 GT를 겹친 그림, `s` 오차를 시간축으로)
- 결론:
  - 미션 예측에 쓸 수 있는지
  - 횡방향을 차로 판단에 쓸 수 있는지
  - 재시작 리셋이 충분한지

## 8. 일정 (제안)
1. 모션캡처 장비 사용 가능 시간 확인 → 수집 1회(2~3바퀴)
2. 전처리 + M1~M4 (분석 도구는 `tools/offline_pipeline/` 확장)
3. M5, M6 → 결과 공유 → 차에 넣을지 결정
